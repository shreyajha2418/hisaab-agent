# Build notes

Kept phase-by-phase for the AI build log. Each entry says what was built and any decision or trade-off worth knowing about.

## Phase 1 — Setup, Blade, PhoneFrame, data

**Scaffold.** `npm create vite@latest . -- --template react-ts`. Removed the template's default assets/styles since Blade owns the visual system.

**Blade installation — two real peer-dependency issues, both resolved, neither a reason to abandon Blade:**

1. **React version ceiling.** Blade's own `peerDependencies` say `react: ">=18"`, but its transitive dependency `@razorpay/i18nify-react@4.0.12` peer-requires `react: "^18.2.0"` — no release of it supports React 19 yet. Vite's react-ts template installs React 19 by default. Fix: pinned `react`/`react-dom`/`@types/react`/`@types/react-dom` to `^18.2.0` before installing Blade. This is the standard fix (match the library's supported range), not a workaround of Blade itself.
2. **React Native peer chain leaking into a web-only install.** `@razorpay/blade` depends on `@floating-ui/react-native` (used internally for cross-platform floating elements), which peer-requires `react-native`, which in turn wants a React 19-range React — a conflict that has nothing to do with how we're using Blade (web only, no RN code path touched). `npm install ... --legacy-peer-deps` is the standard, expected resolution for exactly this situation (a cross-platform library's native peer graph vs. a web-only consumer) and is well short of "Blade can't be set up."

Confirmed installed package: `@razorpay/blade@12.127.0`. Peer deps actually installed: `styled-components@5.3.11`, `@razorpay/i18nify-js@^1.12.3`, `@razorpay/i18nify-react@^4.0.12`, `framer-motion@11.13.3` (per the installed version's real `peerDependencies`, not the doc page's stale pinned versions — Blade's docs page pins `@razorpay/i18nify-js@1.9.3`/`i18nify-react@4.0.8`, which are no longer what the current Blade release actually requires).

**Deploy fix: `.npmrc`.** The `--legacy-peer-deps` flag above was only ever passed on the command line during local setup, so it got baked into `package-lock.json` but not into anything a fresh clone would honor — Netlify's `npm ci` hit the exact same `@floating-ui/react-native` → `react-native@^0.72` → `react@18.2.0` conflict (against the resolved `react@18.3.1`) and failed the build. Fixed by committing `.npmrc` with `legacy-peer-deps=true`, so every install — Netlify's, a fresh clone, CI — picks it up automatically instead of relying on a one-off local flag. Verified by deleting `node_modules` and running `npm ci` (no explicit flag) followed by `npm run build`, both clean.

**Verified working**, not just "installed": wrapped a minimal `App.tsx` (`Box`, `Heading`, `Text`, `Amount`, `Button`) in `BladeProvider` with `bladeTheme`, ran it in a real headless browser, confirmed zero console/page errors and that it rendered with real Blade styling (Razorpay blue button, proper `₹14,600.00` currency formatting via the `Amount` component) — screenshotted at both desktop and 390px-mobile viewport sizes.

**Entry points.** Blade's package exports `@razorpay/blade/components` (all components, `BladeProvider`, `Theme` type) and `@razorpay/blade/tokens` (`bladeTheme`, `bladeNeutralTheme`). Fonts via a single `import '@razorpay/blade/fonts.css'` in `main.tsx` — no Google Fonts or other network dependency, the font files ship in the npm package.

**TypeScript.** Added `resolveJsonModule: true` (needed for the data loader) and a `styled.d.ts` extending styled-components' `DefaultTheme` with Blade's `Theme` type, per Blade's own installation docs.

**PhoneFrame.** A styled-components wrapper, not a Blade component (Blade doesn't have one — it's product UI, not device chrome). Desktop: centered 390×844 frame with a notch, dark backdrop, rounded + shadowed like a phone — built for screen recording the demo. At `max-width: 480px` (an actual phone) all of that chrome disables itself via a media query, so the app is just the page, edge to edge. No JS viewport detection needed.

**Synthetic data.** Seven JSON files in `src/data/`, typed via `src/types/index.ts`. Decisions:

- **Dates are real dates**, not relative offsets — the PRD's own story and "today" both land on 4 Oct 2026, so bill dates (Sep 2026) and the Mehta bill (19 Aug 2026 → 46 days old, PRD says "~45") work out correctly without any fake-clock logic.
- **2 extra open bills** (`V-120`, `K-315`) beyond the 10 implied by the five required scenarios, specifically to hit the spec's exact "12 open bills from 5 customers loaded; 3 already-paid bills skipped" summary text. They're untouched by any event — they exist so the customer dues view has something beyond just the matched bills, and so the 12/3 split is real rather than coincidental.
- **`ai_outputs.json` is keyed by event ID**, not an array, and an event's `eventId` is literally the same ID used in its source record (the Razorpay payment's `id`, the bank statement line's `id`, or the voice note's `id`). One lookup, no secondary join table.
- **Overdue bills (Mehta) are *not* in `ai_outputs.json`.** Unlike payer identification or deduction flagging, "this bill is 45 days old" isn't an AI judgment — it's arithmetic on `bill.date` vs. today. It'll be computed directly by a selector in Phase 2, off the bill data alone, rather than faked as a pre-computed "AI output" it never needed to be.
- **Confidence vs. status are separate axes**, deliberately. Verma's cash entry is `confidence: "high"` (the transcript clearly says "Verma") but `status: "needs_confirmation"` anyway — cash always needs a human nod, regardless of how confident the extraction is. RAJESH K is `confidence: "medium"` and `needs_confirmation` for a different reason — genuine identity uncertainty. Both land in "Needs you" in Phase 2's decision list, but the copy/reasoning shown should read differently, which the data already supports.

**Validation.** `scripts/validate-data.mjs` — a plain Node script (no test framework needed for one-off data validation) that checks cross-references (bills → real customers, allocations → real bills), allocation arithmetic (`amountApplied + remainingOnBill === bill.amount`, `sum(amountApplied) === event.amount`), and the specific numbers the PRD calls out by name (Sharma's split, Kapoor's exact match, Verma's remaining ₹2,000, Gupta's ₹400 short flag, Mehta's day count). Caught one real bug in the script's own check logic during authoring (conflating "short by" with "unapplied") — left as a reminder to re-run this after any data edit, since hand-authoring JSON is exactly where this kind of arithmetic slip happens.

**Not yet built** (Phase 2+): `state/AppStateContext.tsx`, any of the 8 screens, the "agent thinking" delay component, navigation.

**Known trade-off:** `npm run build` warns about an ~880 KB JS bundle — Blade's component barrel is large and nothing is code-split yet. Not a concern for a prototype served locally/from a single page, but worth a per-screen `React.lazy()` pass in Phase 5 polish if bundle size matters for the final submission.

## Phase 2 — Home, Decision list, Match detail

**State.** `src/state/AppStateContext.tsx` — a single `useReducer`, no external state library. Live per-event status (`auto_recorded` / `needs_confirmation` / `confirmed` / `set_aside`) plus a running `billPaid` map (billNumber → cumulative amount applied by resolved events) are the only two pieces of mutable state; everything else (dues, totals, decision-list buckets) is *derived* in `src/state/selectors.ts`, so confirming or undoing one event updates Home, the decision list, and (later) the dues view for free, with nothing to keep in sync by hand. `src/state/NavContext.tsx` is a small in-memory screen stack — same reasoning as Gym Buddy's: this is a linear demo flow, not a real multi-route app, so a router library would be pure overhead.

**The one piece of real (non-AI) logic.** `src/utils/allocate.ts`'s `allocateOldestFirst` is actually computed, not looked up — per the PRD's own F4 framing, oldest-bills-first is a fixed rule, not an AI decision. It's used only when Aman manually reassigns a payment to a different customer via "Change customer" on Match Detail, since that combination (any payment × any of 5 customers) can't be pre-computed in `ai_outputs.json`.

**Confirming an AI suggestion vs. a manual reassignment.** Both end up recorded the same way (an `override` on the event: `{customerId, allocation}`), but they're reached differently: tapping "Yes, this is Gupta Pharmacy" on a still-unidentified event (`payerMatch.customerId === null`) builds that override from the AI's own `suggestedCustomerId` at confirm-time; picking a customer from "Change customer" builds it immediately, before confirming, via `allocateOldestFirst`. Undo clears the override entirely and reverts to `needs_confirmation` — deliberately forgetting a manual reassignment too, so Aman can reconsider from the AI's original suggestion rather than from his own last edit.

**"Agent thinking" delay** (`useAgentThinking` + `ThinkingIndicator`) fires every time Match Detail is opened, not just the first time — simpler than tracking per-event "have I shown this already," and consistent with the hard constraint that this is a deliberate, repeatable UI delay rather than something trying to look like real-time computation.

**Bugs found by actually clicking through it (not just type-checking), fixed before calling this phase done:**

1. **Dates off by one.** `toLocaleDateString`/`toLocaleTimeString` defaulted to the browser's local timezone — UTC in headless Chrome — so a bill dated 1 Sept (midnight IST) displayed as "31 Aug". Fixed by pinning `timeZone: 'Asia/Kolkata'` explicitly in `src/utils/dates.ts`. This matters beyond the test environment: a real viewer outside IST would see the same wrong dates, so the fix is correct regardless of who's looking at it, not just a headless-browser workaround.
2. **The Confirm button never appeared for the app's hero scenario.** `canConfirm` required an *already-identified* customer, but RAJESH K is unidentified until confirmed — so the one case the whole product exists to handle (medium-confidence, needs-a-decision) couldn't be confirmed at all. Fixed to accept either a matched customer or the AI's suggested one.
3. **Confirming a suggestion didn't stick.** Even with (2) fixed, tapping confirm never recorded *which* customer was confirmed (no override was created for the "accept the AI's own suggestion" path, only for manual reassignment), so the screen kept showing "RAJESH K" forever instead of switching to "Gupta Pharmacy". Fixed in the `CONFIRM_EVENT` reducer case — see above.
4. **Same money counted as two different problems.** Gupta's `G-201` (33 days old) crossed the overdue threshold independently of the RAJESH K match that would clear it, so it showed up as both "RAJESH K ₹14,600" and a separate "Gupta Pharmacy — 33 days overdue" row. Fixed `getOverdueBills` to exclude any bill already referenced in a pending `needs_confirmation` event's allocation.
5. **Badge copy went stale.** The confidence badge reused the word "Needs your input" for medium confidence, which was wrong once that event was actually confirmed (still showed "needs your input" after it no longer did), and wrong again when reused for overdue bills (a "Low confidence" badge on a bill that was never matched or mismatched by the AI at all — it's just old). Badge copy is now purely about AI confidence; overdue bills get their own `Badge color="negative"` labeled "Overdue".

None of these were caught by `tsc` or `oxlint` — all five only showed up by running the app in a real browser and clicking through the actual RAJESH K / undo / overdue flows, which is why Phase 2 (and every phase after it) gets verified that way before being called done, not just compiled.

**Verified:** `tsc -b`, `oxlint`, `npm run build`, and `scripts/validate-data.mjs` all clean. Full click-through in a headless browser: Home → Decisions → RAJESH K match detail → confirm → title updates to "Gupta Pharmacy" and moves to "Done automatically" → Undo on Sharma → re-appears in "Needs you" with correct re-confirm copy → Home totals (decisions-waiting count, outstanding total) update live at every step. Set-aside section expands/collapses and shows all three non-customer credits with correct reasoning.

**Not yet built** (Phase 3+): the dedicated RAJESH K-style payer-confirmation screen (Match Detail's generic Confirm button covers the mechanics already), the ₹400 short-payment flag's own Accept/Question-it interaction (currently just displayed, not actionable), the Memory screen, Settings tab content, cash voice note flow, Upload bills, Customer dues view.

## Phase 3 — RAJESH K confirmation, ₹400 flag, Memory

**No new screen needed for payer confirmation.** Phase 2's generic Match Detail (Confirm / Change customer / Undo) already handles RAJESH K mechanically — the only things actually missing were: (1) feedback that something was *learned*, and (2) a way to act on the deduction flag. Both are additive on top of the existing screen rather than a new one, so the PRD's 8 screens stay at 8 — Match Detail just does more once an event is confirmed.

**"Remembered" toast.** `useToast()` fires once, only the first time an unidentified raw label (`payerMatch.customerId === null`) gets an override — re-confirming after an Undo doesn't re-toast, since the override already exists at that point. `<ToastContainer offsetBottom={72} />` is mounted once in `App.tsx`, inside the phone frame, offset to clear the bottom nav.

**Deduction flag becomes interactive only after confirming.** Before confirmation, `short_payment` still renders as the plain informational `FlagBanner` from Phase 2 — matches the PRD's "after confirming the match, flag it" framing; there's nothing to accept or question about money that isn't recorded yet. Once `liveStatus === 'confirmed'`, the same flag renders as `DeductionFlag` instead, with three states driven by `state.flagResolutions[eventId]` (`'pending' | 'accepted' | 'questioned'`, absent = pending):
- **Pending** — the flag text plus Accept / Question it buttons.
- **Accepted** — a positive `Alert` ("₹400 written off as a likely deduction"). This is a demo acknowledgement only — nothing in the data actually changes, `G-230` still correctly shows "₹400 still pending" in the allocation list, since the PRD never asked the prototype to simulate writing off a bill balance.
- **Questioned** — a drafted, customer-facing message in a read-only box ("Hi Gupta Pharmacy, this payment is ₹400 short…"). Per the hard constraint (no backend, nothing really sent), there's no send button — it's presented as "ready to send", which is the honest scope of a clickable prototype.

Undoing a confirmed event clears its `flagResolutions` entry too, so re-confirming starts the flag fresh at pending rather than remembering a stale Accept/Question choice from before.

**Decision list surfaces pending flags as their own row.** New selector `getPendingDeductionFlags` (in `selectors.ts`) returns confirmed events with an unresolved `short_payment` flag; `DecisionListScreen` renders them in "Needs you" with a `Badge color="notice"` labeled "Flagged" and a "₹400 short — tap to review" subtitle, tapping through to the same Match Detail screen. They drop out of "Needs you" the moment Aman accepts or questions the flag — `getDecisionsWaitingCount` was updated to include them so Home's "N decisions waiting" count stays accurate throughout.

**Memory screen lives inside Settings**, not as a separate tab — the PRD lists "Memory" as one of 8 screens but the nav only has three tabs (Home/Decisions/Settings), so it's a section of the Settings screen alongside Reset demo and the required prototype disclosure. Each learned identity (`"RAJESH K" → Gupta Pharmacy"`) has its own Remove button; removing it only forgets the *memory entry* — the underlying event stays confirmed as Gupta Pharmacy, since "forgetting" a name shouldn't un-confirm real (demo) money. The next time that same raw label shows up, there's no re-recognition logic to forget anyway (one event per raw label in this dataset), so Remove's only real purpose here is giving Aman a visible, working control, exactly as the PRD's Memory screen asks for.

**Reset demo moved from a bare button to a two-tap confirm** ("Reset demo" → "Yes, reset demo" / "Cancel") — a reasonable guard against wiping a live demo recording by a stray tap, without needing a full modal component for a prototype.

**Verified:** `tsc -b`, `oxlint`, `npm run build`, `scripts/validate-data.mjs` all clean. Full click-through in a headless browser covering both flag paths: confirm RAJESH K → toast fires once → flag shows as pending in both Match Detail and the Decisions "Needs you" list → Question it → drafted message renders, row drops out of "Needs you" → back out, confirm Memory shows the learned entry → Remove it → event stays confirmed as Gupta Pharmacy → Reset demo (with confirm step) → Decisions, Settings, and Memory all revert to the pristine starting state. Also verified the Accept path separately (same flow, ends in a positive "written off" alert instead). Zero console/page errors across both runs.

**Not yet built** (Phase 4+): cash voice note flow, Upload bills, Customer dues view.

## Phase 4 — Add cash, Upload bills, Customer dues

**Add cash (voice note).** `AddCashScreen` replays the PRD's own demo moment — there's exactly one voice note in the synthetic data (`voice_001`, Verma ₹8,000), so "Record voice note" always produces the same transcript rather than accepting arbitrary new input; that's consistent with the no-backend constraint, not a shortcut around it. The flow is four local `Stage`s (`idle → recording → transcribed → thinking → matched`), each a plain `setTimeout`, ending on a "Review match" button that hands off to the existing Match Detail screen for `voice_001` — Phase 2/3's confirm mechanics handle the rest, so this screen only owns the capture moment (mic tap, waveform-style "Recording…", the transcript appearing on screen per the PRD's "transcription shown on screen" demo beat), not a second confirmation UI.

**Upload bills.** `UploadBillsScreen` is a single mocked action ("Upload outstanding_bills.xlsx") rather than a real file picker, since the bills are already seeded — there is no second data set to swap in. It replays F1's described behaviour as a static summary computed from the real data: `12 open bills from 5 customers` / `3 already-paid bills skipped (duplicates by bill number)`, numbers pulled live from `bills.json` (not hand-typed), so they can't drift from the actual seeded data. "Done" returns to Home via `switchTab`.

**Customer dues view (F8).** New `CustomerDuesScreen` — total owed, open bills (with an `Overdue` badge past the same 30-day threshold the decision list uses), and recent payments (confirmed/auto-recorded events, newest first, tapping through to that event's Match Detail). New selector `getCustomerRecentPayments` filters `getAllEvents` by *effective* customer — so Gupta Pharmacy's dues view correctly includes the RAJESH K payment once confirmed, even though the raw bank line never named Gupta Pharmacy. Reuses `DecisionCard` for both lists rather than hand-rolling rows, keeping the row markup (and its no-nested-`<button>` fix from Phase 2) in one place.

**Entry points**, since nothing linked to these screens before now: Home gained a "Quick actions" row (`Add cash`, `Upload bills`, both already in `NavContext`'s `Route` type since Phase 2 but unused until now); the Decisions list's overdue rows now navigate to that bill's customer's dues view instead of being inert; Match Detail gained a "View {customer}'s dues" button, shown whenever the event has a resolved customer (matched or confirmed).

**Verified:** `tsc -b`, `oxlint`, `npm run build`, `scripts/validate-data.mjs` all clean (same two pre-existing Fast-Refresh warnings from Phase 2, nothing new). Full headless-browser click-through: Home → Upload bills → upload → correct 12/5/3 summary → Done → back on Home; Home → Add cash → record → transcript appears → Match it → thinking → matched summary → Review match → Match Detail (Verma) → Confirm → View dues → Verma's dues view shows the right remaining bills and the cash payment just confirmed; Decisions → tap Mehta's overdue row → dues view shows M-090 with the Overdue badge and correct ₹18,500/46-days figures. Zero console/page errors throughout.

**Not yet built** (Phase 5): transition polish, empty states, a visible Reset-demo entry point was already added in Phase 3 — remaining Phase 5 scope is primarily visual/interaction polish and a final README pass per the original plan.
